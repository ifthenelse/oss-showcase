# Stage state and deterministic generation

Run commands from the repository root. Set `showcase_skill` to the resolved skill folder and use Python 3.10 or later.

## Facts and evidence

Use `.agents/product-facts.json` for evidence, `.agents/product-marketing.md` for positioning and `.agents/brand-guidelines.md` for visual and voice decisions. Initialize missing files from the corresponding templates and reuse approved assets under `docs/assets/`. Use the profile matching the project's primary user entry point. Populate the facts JSON with a verified summary, setup, example and optional observed result. Keep general positioning and wording decisions in the two Markdown context files. Use `sections` objects with `title` and `body`, adapted from the profile. Map keys `summary`, `setup`, `example`, `result` (if present), and each section title to arrays of existing repository-relative evidence paths. Inspect the actual content and record exact line, test, commit or output provenance in the context files where helpful. The script checks that listed files exist. It cannot assess truth.

Use `assets` entries like `"social": {"path": "assets/social.png", "alt": "Project name and tagline"}`. Roles are `logo`, `favicon`, `social`, `demo` and `poster`. For a demo also include a `caption` that describes the action and result. Files belong under `docs/assets/`. Record `release` for a showcase tied to a specific release. Use GitHub's `/releases/latest` link for evergreen installation guidance. Use the selected language for README and site copy, captions, metadata, release and launch drafts, and handoffs. Set the facts `lang` and localize the `quickstart`, `repository`, and `demo` labels. Localize fixed visible and accessible template text using new overrides or a separate preview. Preserve commands and code examples.

## Refresh plan

Treat stage inputs as read-only evidence. A stale fingerprint identifies material to review. Use `preview` in a fresh scratch directory, then update only verified skill-owned outputs. Leave a separate draft for changes to existing project files. Preserve hand-maintained README and site sections, working install commands, existing publication settings and verified assets. Carry forward evergreen release links as tags change. Leave build, test, release and deployment logic in the target repository intact. Report changes that would require altering project behavior as follow-up work.

Keep `.agents/showcase/stages.json` current using the supplied example. Declare exact repo-relative file paths, including optional source paths that may appear later. In a monorepo include only the selected package and relevant shared inputs. Discover new stage inputs from the current source tree and add them to the spec before checking status. Keep package manifests, entry points, tests and lockfiles in appropriate input sets.

```sh
python3 "$showcase_skill/scripts/showcase.py" status .agents/showcase/stages.json
python3 "$showcase_skill/scripts/showcase.py" record .agents/showcase/stages.json demo
```

Record after a successful review, never merely to clear a stale flag. Compare the declared input and output digests in `.agents/showcase/state.json` to find the changed files. Track creative outputs and tool or template revisions as relevant. For a tool or skill revision that lives outside the repo, capture its version or resource digest in a local stage-input file. An already approved mark is a brand input for derived variants. Track the actual logo, favicon and preview paths consumed by the presentation. Remove optional example outputs from the stage spec when the project does not use them. Demo inputs should include fixture, recording recipe, tool versions, displayed release if any and affected entry points. Keep prose-only edits outside the recording fingerprint. A source change calls for checking the affected scenario, then keeping the existing recording when the observable result remains accurate. Missing or edited output requires review before accepting its hash.

## Render and review

```sh
python3 "$showcase_skill/scripts/showcase.py" plan
python3 "$showcase_skill/scripts/showcase.py" apply
python3 .agents/showcase/validate.py
```

Use `--keep-readme` on both plan and apply for a hand-maintained README. Plan and apply preserve an existing Pages workflow, including one generated by the skill. Use `--keep-workflow` to omit new workflow scaffolding when the project already has a deployment path. Conflicts with other hand-maintained files stop the render before output writes. Use `preview` with a fresh scratch destination to review candidates for manual reconciliation.

For project-specific design, create template overrides at unused paths under `.agents/showcase/templates/` or use a separate draft when an override already belongs to the project. Keep the output and validation contract. Use the existing site as read-only evidence when the starter cannot represent it.

The plan compares content hashes. Apply serializes writers, writes files atomically and preserves the last generated hash after each write. Identical output is left untouched and does not establish ownership. Only hashes recorded after a successful generator write establish ownership. Earlier ledgers may include hashes of pre-existing files, so those hashes are insufficient for overwrites. Public files removed from the artifact manifest, such as a disabled `llms.txt`, are retained on disk and reported if previously generated. Report obsolete paths to the maintainer when the repo serves `docs/` directly. Inspect an abandoned write lock before removing the empty lock directory after an interrupted run.

Validate the final Git diff and inspect public artifacts before finishing. Approval of generated bytes is reflected in the manifest's hashes, so apply only to content that passes review. The deterministic validator checks the generated static contract and a few obvious secret patterns. Use the stage gates for copy, accessibility, external link behavior, runtime truth, media contents and secrets.
